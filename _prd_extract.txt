1. Peran dan Tujuan
Kamu adalah senior Laravel backend engineer. Bangun REST API untuk Humify, aplikasi HRIS presensi. Yang dibangun hanya backend, tanpa UI. API dipakai oleh dua klien: aplikasi mobile (presensi, pengajuan cuti, review tim) dan web portal (workspace karyawan, review manager, administrasi HR, pengelolaan akun Super Admin).
Hasil akhir: proyek Laravel yang dapat dijalankan, bermigrasi, ter-seed, teruji, dan terdokumentasi (OpenAPI).
2. Konteks Produk
Humify mencatat presensi dengan tiga verifikasi: wajah, lokasi (area kerja yang diizinkan), dan waktu (waktu server). Status presensi dihitung oleh backend, bukan oleh perangkat pengguna.
Role	Kemampuan
employee	Presensi sendiri, daftar wajah acuan (sekali), riwayat, saldo dan pengajuan cuti, ubah data kontak sendiri.
manager	Semua kemampuan employee, ditambah review presensi dan pengajuan cuti bawahan langsung (supervisor_id), riwayat tim.
hr_admin	Semua kemampuan employee, ditambah review di seluruh perusahaan, kelola karyawan, foto wajah acuan, shift, lokasi kerja, jenis cuti dan saldo awal, laporan bulanan.
super_admin	Semua kemampuan hr_admin, ditambah kelola akun dan role. Hanya Super Admin yang boleh mengubah role.
Tidak termasuk: lembur, payroll, notifikasi push, kalender hari libur nasional.
3. Stack dan Konvensi
•Laravel 12, PHP 8.3, MySql, Laravel Sanctum (personal access token untuk mobile dan web), Pest untuk test.
•Arsitektur: Controller tipis, Form Request untuk validasi, Service/Action class untuk logika bisnis, Eloquent Model, API Resource untuk output, Policy untuk otorisasi, PHP backed enum untuk status.
•Semua rute di bawah /api/v1. Respons JSON. Sukses: { data, meta }. Error: { message, code, errors } dengan code berupa SNAKE_CASE yang stabil (daftar di Bab 7).
•Waktu disimpan sebagai timestamptz (UTC). Zona waktu perusahaan ada di tabel settings (default Asia/Jakarta), dan attendance_date dihitung berdasarkan zona itu.
•employees dan users memakai UUID, tabel lain bigint.
•Jangan memakai trigger database. Logika yang sebelumnya ada di trigger (potong saldo cuti, penandaan absensi cuti, validasi shift) ditulis di Service layer dalam transaksi database, lengkap dengan test.
•Pilih opsi paling sederhana jika ada hal yang ambigu, lalu catat di bagian Asumsi pada README. Jangan berhenti untuk bertanya kecuali benar-benar terblokir.
4. Skema Database
Gunakan hris_schema.sql (lampiran) sebagai dasar untuk tabel: departments, positions, employees, users, work_shifts, attendances, leave_types, leave_balances, leave_requests. Tulis ulang sebagai migration Laravel (bukan menjalankan SQL mentah), dengan perubahan berikut.

Desain UI berbahasa Inggris, jadi seluruh nilai status di database dan API memakai nilai baru ini. Simpan sebagai kolom string dengan CHECK constraint, dan petakan ke PHP backed enum.

4.2 Perubahan dan tabel tambahan
Perubahan ini berasal dari desain UI dan belum ada di hris_schema.sql.
•employees: tambah personal_email, emergency_contact_name, emergency_contact_phone, emergency_contact_relationship, face_registered_by (FK ke users, nullable). Kolom address dipakai sebagai alamat rumah.
•work_shifts: start_time dan end_time dibuat nullable. Desain UI menampilkan kondisi shift belum dikonfigurasi, jadi shift yang jamnya masih kosong tidak boleh dipakai untuk check-in.
•work_locations (baru): id, name, latitude, longitude, radius_meters, is_active. Dipakai untuk memvalidasi area kerja yang diizinkan (geofence) saat check-in dan check-out.
•attendances: tambah untuk check-in dan check-out masing-masing work_location_id, geofence_valid (boolean), dan distance_m. Baris yang dibuat sistem dari cuti disetujui langsung berstatus review approved tanpa reviewed_by. Hari libur (Sabtu dan Minggu) tidak disimpan, tetapi disintesis oleh API sebagai day_off dengan review not_applicable. Kolom review_note dipakai untuk catatan approve (opsional) dan alasan reject (wajib).
•attendance_attempts (baru, hanya ditambah, tidak diubah): id, employee_id, type (check_in atau check_out), outcome, failure_code, face_score, distance_m, work_location_id, created_at. Mencatat setiap percobaan, termasuk yang gagal. Foto dari percobaan gagal tidak disimpan.
•leave_types: tambah attendance_status (on_leave, sick_leave, atau authorized_absence) agar penandaan absensi saat cuti disetujui mengikuti jenis cuti, dan tracks_balance (boolean).
•leave_requests: tambah canceled_by (FK ke users) dan canceled_at.
•settings (baru): key (unik) dan value (jsonb). Isi awal: company_timezone, face_match_threshold (default 80), close_day_time.
•audit_logs (baru): id, actor_user_id, action, subject_type, subject_id, changes (jsonb), ip, created_at.
•Index: unik (employee_id, attendance_date) pada attendances; (review_status, attendance_date); (status, start_date) pada leave_requests.
5. Aturan Bisnis
5.1 Autentikasi
Login memakai username dan password. Batasi 5 percobaan per menit per kombinasi username dan IP; jika terlampaui kembalikan 429 dengan retry_after. Semua kegagalan login lain memakai pesan generik yang sama (tidak membedakan username salah atau password salah). Akun nonaktif atau karyawan yang tidak berstatus active tidak bisa login.
5.2 Cakupan data
•employee: hanya data milik sendiri.
•manager: data sendiri ditambah bawahan langsung (employees.supervisor_id sama dengan karyawan yang login), tidak rekursif.
•hr_admin dan super_admin: seluruh perusahaan.
•Tidak seorang pun boleh me-review record miliknya sendiri.
5.3 Kategori kerja dan shift
Karyawan regular hanya boleh memilih shift berkategori regular. Karyawan shifting hanya boleh memilih shift berkategori shifting (Shift 1, 2, 3). Validasi dilakukan di server.
5.4 Foto wajah acuan
Karyawan mendaftarkan sendiri sekali. Setelah terdaftar, hanya hr_admin atau super_admin yang dapat menggantinya, dan penggantian memerlukan konfirmasi eksplisit serta masuk audit_logs. Check-in dan check-out ditolak jika wajah acuan belum terdaftar.
5.5 Check-in dan check-out
Urutan validasi:
1.Pengguna terautentikasi dan karyawan berstatus active.
2.Wajah acuan sudah terdaftar.
3.(Check-in) Shift valid untuk kategori kerja dan jamnya sudah dikonfigurasi.
4.Tidak duplikat. Jika sudah check-in, kembalikan 409 ALREADY_CHECKED_IN beserta record yang sudah ada di data, supaya klien yang kehilangan respons dapat memulihkan keadaan tanpa membuat data ganda. Dukung juga header Idempotency-Key.
5.Geofence: hitung jarak Haversine ke setiap work_locations aktif. Valid jika berada dalam radius salah satunya.
6.Verifikasi wajah lewat interface FaceVerifier (hasil: matched dan score), dibandingkan dengan face_match_threshold.
7.Simpan dalam satu transaksi dan catat di attendance_attempts. Waktu yang tercatat adalah waktu server, bukan waktu dari perangkat.
Jika langkah 5 atau 6 gagal, tidak ada presensi yang tersimpan (hanya attendance_attempts), dan respons 422 membawa kode OUTSIDE_PERMITTED_AREA atau FACE_MISMATCH. Jika layanan verifikasi wajah timeout atau error, kembalikan 503 FACE_SERVICE_UNAVAILABLE dan jangan menyimpan apa pun.
Respons sukses memuat: waktu terkonfirmasi server, shift, status, review_status pending, hasil wajah (verified, score), dan hasil lokasi (valid, nama lokasi kerja).
Check-out mencari presensi terbuka terbaru (ada check-in, belum ada check-out) dalam 24 jam terakhir, lalu mengharuskan verifikasi wajah dan lokasi yang sama.
Buat FaceVerifier sebagai interface dengan driver fake (untuk development dan test, dapat dikonfigurasi cocok atau tidak) dan satu kerangka driver penyedia nyata. Jangan mengunci ke vendor tertentu.
5.6 Perhitungan status (tanpa toleransi)
•late jika check_in melewati start_time shift pada attendance_date. late_minutes = pembulatan ke atas dari selisih detik dibagi 60.
•Saat check-out sebelum end_time: early_leave_minutes dihitung dengan cara yang sama. Status menjadi left_early hanya jika karyawan tidak terlambat. Karyawan yang terlambat tetap late, dan menit pulang cepatnya tetap tersimpan.
•work_minutes = selisih check-in dan check-out.
•Shift overnight: end_time jatuh di hari berikutnya, dan attendance_date adalah tanggal check-in.
5.7 Hari kerja dan penutupan hari
Hari kerja adalah Senin sampai Jumat; tidak ada kalender libur nasional. Buat Artisan command terjadwal attendance:close-day (jalan harian pada close_day_time) yang membuat record absent dengan review pending untuk setiap karyawan aktif yang tidak punya presensi dan tidak punya cuti disetujui pada hari kerja sebelumnya. Command harus idempoten.
5.8 Review presensi
Hanya record berstatus review pending yang dapat di-review. Approve (catatan opsional) atau reject (alasan wajib). Isi reviewed_by, reviewed_at, review_note. Record yang sudah diputuskan bersifat read-only (409 ALREADY_RESOLVED). Menyetujui presensi tidak menyetujui cuti.
5.9 Pengajuan cuti
•Submit: jenis cuti aktif, start_date tidak setelah end_date, total_days dihitung server (jumlah hari kerja dalam rentang) dan harus lebih dari 0, tidak tumpang tindih dengan pengajuan pending atau approved milik sendiri, dan lampiran wajib jika jenis cuti mensyaratkannya (pdf/jpg/png, maksimal 5 MB, disimpan privat). Saldo tidak berubah saat pending.
•Approve (satu transaksi): periksa ulang saldo bila tracks_balance (jika kurang, 422 INSUFFICIENT_BALANCE); tambah used_days; buat atau perbarui attendances untuk tiap hari kerja dalam rentang dengan status dari leave_types.attendance_status dan review approved. Jangan menimpa record yang sudah memiliki check_in_time; kembalikan daftar tanggal yang dilewati di meta.
•Reject: alasan wajib dan terlihat oleh karyawan.
•Cancel: hanya pemilik dan hanya saat pending (isi canceled_by dan canceled_at). Membatalkan pengajuan yang sudah disetujui tidak didukung pada MVP (409).
5.10 Menonaktifkan karyawan
Set status karyawan menjadi inactive, nonaktifkan akun login, cabut semua token. Data historis tetap utuh. Endpoint memerlukan konfirmasi eksplisit.
5.11 Laporan bulanan
Hitung dari record berstatus review approved secara default; parameter include_pending=true menyertakan yang pending. Metrik: present_days (present, late, left_early), late_records, late_minutes, leave_days (on_leave, sick_leave, authorized_absence), absent_days.

7. Keamanan, Audit, dan Kode Error
•File privat: foto dan lampiran disimpan di disk privat dengan nama acak. Tidak ada URL publik; akses lewat endpoint terotorisasi atau signed URL berumur 5 menit.
•Validasi upload: foto jpg atau png maksimal 5 MB; lampiran pdf, jpg, atau png maksimal 5 MB.
•Rate limit: login 5 per menit; check-in dan check-out 10 per menit per pengguna.
•Privasi: lokasi hanya diperiksa saat aksi presensi dan tidak dilacak terus-menerus. Jangan menulis foto atau koordinat mentah ke log aplikasi.
•Audit: audit_logs wajib untuk approve dan reject presensi atau cuti, penggantian foto acuan, perubahan akun dan role, deaktivasi karyawan, dan perubahan settings.
•Otorisasi: setiap resource punya Policy, dan setiap role diuji di test otorisasi.
•Lain-lain: CORS dikonfigurasi untuk domain web portal, dan masa berlaku token dapat diatur lewat konfigurasi.
